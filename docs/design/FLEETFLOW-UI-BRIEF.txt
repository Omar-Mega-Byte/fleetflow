You are performing a full product-design and frontend overhaul of FleetFlow.

FleetFlow is a Java/Spring delivery orchestration learning backend with a real frontend, real backend workflows, and real operational behavior. The current frontend is functionally usable but visually weak, generic, sparse, and does not communicate the sophistication of the backend.

Your task is NOT to merely “make it prettier.”

Your task is to transform FleetFlow into a premium, portfolio-grade, production-quality logistics product experience that feels deliberately art-directed, technically credible, visually distinctive, responsive, animated, and coherent across the entire system.

The quality bar should feel comparable to excellent modern SaaS and infrastructure products such as Linear, Stripe, Vercel, Ramp, modern Uber operational tooling, premium logistics dashboards, and high-end developer tools — while still being original and specific to FleetFlow.

The final result must NOT look like:
- a generic Tailwind admin template
- a CRUD dashboard
- an AI-generated SaaS interface
- a dashboard full of random metric cards
- a page dominated by empty whitespace
- a “glassmorphism everything” design
- a neon cyberpunk UI
- a generic purple/blue gradient startup site
- a collection of shadcn components with no design system
- a marketing landing page pretending to be an operational application

FleetFlow must feel like a REAL-TIME LOGISTICS OPERATING SYSTEM.

- missing UX around existing backend features
- duplicated components
- weak visual patterns

==================================================
4. DESIGN PRINCIPLES
==================================================

The final design must follow these principles:

1. PURPOSEFUL
Every visual element should communicate something.

2. OPERATIONAL
The interface should feel alive and connected to real system state.

3. PREMIUM
Spacing, typography, hierarchy, and interaction quality matter more than visual noise.

4. RESTRAINED
Avoid gratuitous effects.

5. DYNAMIC
Motion should reflect real state transitions.

6. DOMAIN-SPECIFIC
It should unmistakably feel like a logistics product.

7. CLEAR
Users should understand current system state immediately.

8. SCALABLE
Design components should support more features later.

9. ACCESSIBLE
Keyboard, focus, contrast, labels, and reduced-motion support are required.

10. FAST
Do not sacrifice performance for spectacle.

8. MOTION SYSTEM
==================================================

Create a real motion language.

Do not use random animations.

Motion should communicate:
- page entry
- loading
- status changes
- navigation
- live updates
- selection
- route progress
- timeline progression
- dispatch activity

Use Motion/Framer Motion for most UI transitions if appropriate.

Use GSAP only for genuinely complex motion:
- route drawing
- advanced SVG animation
- major timeline sequences
- map storytelling
- cinematic onboarding sequence

Recommended timing:
micro interaction: 120–180ms
standard transition: 180–260ms
complex transition: 260–400ms

Use:
- subtle spring physics
- opacity
- 4–12px translations
- scale around 0.98–1.02
- shared layout transitions
- staggered entry
- smooth height expansion
- animated progress

Avoid:
- giant bounce
- excessive parallax
- constant pulsing
- long easing
- flashy transitions on every click

Respect:
prefers-reduced-motion

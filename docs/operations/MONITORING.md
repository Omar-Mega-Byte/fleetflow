# Local monitoring and alert runbook

**Scope:** Phase 11 synthetic local demo. The private scrape path, provisioning APIs, dependency/readiness alerts, and a signed outbox backlog drill were exercised on 2026-10-07; see [observability evidence](PHASE11_OBSERVABILITY_EVIDENCE.md). This is not a public production monitoring deployment.

## Dashboard design decision

The operator question is “is a customer command working, and if not, is the cause the API, a dependency, or delayed derived work?” The reference lock uses Grafana's native dark operator dashboard as the primary surface and [Grafana's dashboard guidance](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices/) for a general-to-specific order. The bundled Refero craft color guide supplies the narrow secondary rule: neutrals carry most information; warning and danger colors signal thresholds only. Live Refero research was unavailable because its connector returned `NO_SUBSCRIPTION`.

The first row shows six small status numbers: scrape, PostgreSQL, Redis, oldest pending outbox age, failed outbox rows, and active SSE streams. Lower rows show API symptoms, outbox/consumer progress, then offer/recovery and incident queues. Each panel has a description naming its source meter or PromQL. No order IDs, actor IDs, coordinates, or exception text appear in metric labels. Grafana's own theme, type, and keyboard behavior are preserved; this dashboard adds no custom decorative palette or imagery.

## Day 1 health and signal semantics

`/actuator/health/liveness` reports process liveness only. Readiness includes `readinessState` and PostgreSQL; it excludes Redis, Kafka and Keycloak so an optional or recoverable dependency outage does not trigger an application restart loop. PostgreSQL loss makes readiness `DOWN` (HTTP 503); liveness remains `UP`. Redis outage keeps the app ready, but Redis-backed route budgets use a bounded process-local fallback, location/heartbeat writes fail closed with 503, and tracking returns no Redis position while counting a fixed `redis_error` outcome. Kafka outage does not roll back a committed business transaction; outbox publication retries and its pending/oldest gauges rise. Uncached JWKS fetch failure returns safe HTTP 503 `IDENTITY_UNAVAILABLE`; already cached valid-key tokens remain verifiable until expiry. OIDC validation fails closed when signing keys cannot be obtained; identity-provider login/validation is not represented by the readiness probe.

Management detail and metrics remain restricted: public health responses do not show component detail, `/actuator/metrics` requires `DISPATCHER`, and Prometheus is exposed only in the private monitoring profile on port 9095 without a host port.

## Start and access

1. Put a private `GRAFANA_ADMIN_USER` and `GRAFANA_SECRET_FILE=.env.grafana-credential` in ignored `.env`, alongside the existing local stack values. Create `.env.grafana-credential` as an ignored file containing a long random password, with access restricted to the operator. Grafana reads it through `/run/secrets/grafana_admin_credential` using its documented `GF_SECURITY_ADMIN_PASSWORD__FILE` setting. Do not put the password itself in `.env` or `.env.example`.
2. Inspect cached images before any pull. The optional overlay uses the cached, digest-pinned `prom/prometheus:v3.15.0` and `grafana/grafana:13.1.6` images. Pull only an unavailable image, and recheck the digest after any intentional version change.
3. Start **one** isolated Compose project with `docker compose --env-file .env -f compose.yaml -f compose.monitoring.yaml --profile monitoring -p fleetflow-phase11-demo up -d --build --pull never`. Do not point this project at an existing data volume. The overlay changes only this project's app to `prod,monitoring` and moves its Actuator endpoints to container port `9095`.
4. Grafana is reachable only at `http://127.0.0.1:${GRAFANA_PORT:-3000}` on the host. Prometheus and the management port have no published host port. Log in with the private Grafana credentials. Open **FleetFlow / local operations** in the FleetFlow folder.
5. For a clean teardown of only this disposable project, stop it with `docker compose --env-file .env -f compose.yaml -f compose.monitoring.yaml --profile monitoring -p fleetflow-phase11-demo down`. Preserve volumes unless this project's identity, path, and disposable status have been verified explicitly. Never issue a `down --volumes` against the normal `fleetflow` project.

For optional Discord delivery, create a webhook for a private operator channel and save its URL in a private file. On the tested Windows Docker Desktop host, binding a file directly from `%LOCALAPPDATA%` made the container see a directory, so copy it to a Git-ignored `.env.discord-webhook` file in the repository root and verify `git check-ignore .env.discord-webhook`. Do not paste the URL into Compose, an environment variable, logs, or Git. Set `$env:DISCORD_WEBHOOK_FILE='.env.discord-webhook'`, then include `-f compose.alerting.yaml` after `compose.monitoring.yaml` in the same Compose project and use `--profile monitoring`. This adds private Alertmanager and points Prometheus at it; no Alertmanager host port is published. The webhook is mounted as a file secret at `/run/secrets/discord_webhook_url`. The base monitoring overlay remains usable without a Discord destination.

Validate the optional configuration with `docker compose ... -f compose.monitoring.yaml -f compose.alerting.yaml config --quiet`, then run `promtool check config /etc/prometheus/prometheus-alerting.yml` inside the running Prometheus container and `amtool check-config /etc/alertmanager/alertmanager.yml` inside the running Alertmanager container. To exercise delivery on a **disposable** project, stop only its app, wait for `FleetFlowReadinessUnobservable` to fire, check Alertmanager's Discord notification counters, restart the app, and confirm alert resolution. HTTP success and counters prove the Discord API accepted delivery; an operator must also confirm the intended channel displays the message. `Invoke-Phase11ScheduledBackup.ps1` uses the same private URL file for a generic backup-failure notification and keeps a failed backup nonzero.

The Prometheus scrape endpoint is anonymous **only within the `monitoring` profile** and is intended for the private, unexposed Compose management port. Business routes still require Keycloak-signed OIDC and PostgreSQL scope checks. The normal app profile exposes no Prometheus endpoint; `/actuator/metrics` continues to require `DISPATCHER`. The optional overlay must not be used on an internet-facing host without a separate network and authentication review.

## Signal map

| Operator question | Meter/PromQL source | Expected interpretation |
| --- | --- | --- |
| Is the app scrape reachable? | `up{job="fleetflow"}` | `1` means the private management endpoint answered; it is not proof that every business dependency works. |
| Can the database and Redis answer? | `fleetflow_operations_database_available`, `fleetflow_operations_redis_available` | Refreshed every 15 seconds. `0` means a failed probe; the DB-dependent queue gauges become `-1` when PostgreSQL is unavailable. |
| Are requests healthy? | `http_server_requests_seconds_count`, `http_server_requests_seconds_bucket` | Business route 5xx/s and five-minute p95. The histogram is enabled only in the monitoring profile. Exclude expected `409` and `429` from the 5xx symptom panel. |
| Is durable async work draining? | `fleetflow_outbox_pending`, `fleetflow_outbox_failed`, `fleetflow_outbox_oldest_seconds`, `fleetflow_outbox_publish_total` | Pending/failed/age are database snapshots refreshed every 15 seconds, including when publication is paused. The publish counter records acknowledged publications and bounded failures, not business commits. |
| Are consumers making effects? | `fleetflow_events_projected_total`, `fleetflow_events_quarantined_rows` | Fixed labels `consumer` and `outcome`; processed effects count only after their PostgreSQL transaction commits. Quarantined rows need operator review. |
| Are recovery and tracking bounded? | `fleetflow_offers_overdue`, `fleetflow_recovery_due`, `fleetflow_incidents_open`, `fleetflow_incidents_oldest_seconds`, `fleetflow_tracking_active`, `fleetflow_tracking_connections_total` | The first four are durable snapshots; active streams and fixed connection outcomes are in-process. |
| Are dispatch and offers completing? | `fleetflow_dispatch_outcomes_total`, `fleetflow_offer_outcomes_total`, `fleetflow_offer_responses_total` | Bounded outcome labels only; no actor, order, token, coordinate or free-text labels. |
| Are rate limits rejecting work? | `fleetflow_route_limit_total{class,outcome}`, HTTP request 429 count | Class and outcome are bounded; no identity label. Alert threshold is sustained HTTP 429 pressure. |
| Is there Kafka consumer lag? | Not exported in the current single-service setup | Quarantine and projection counters are available; broker/group lag still needs a supported exporter or an explicit manual check before target operations. |

`X-Correlation-ID` is validated or generated for HTTP requests. JSON application logs carry it through the synchronous command and after-commit outbox insertion. Search the committed `eventId` and `orderId` in the `outbox.committed`, `outbox.published`, and `event.projected` records to follow asynchronous work. They are safe identifiers in logs, never metric labels. A Kafka outage can delay publication while leaving the business command committed.

## Alert exercises and operator actions

Every rule is owned by the local operator and has a bounded evaluation window. In the base local demo, alerts appear in Prometheus/Grafana. The optional Alertmanager overlay can send them to Discord. Capture the transition from pending to firing and back to inactive during the Phase 11 drill before marking an alert verified.

### Outbox backlog

`FleetFlowOutboxBacklog` fires after pending age exceeds 30 seconds for one minute; `FleetFlowOutboxFailed` fires after a failed row exists for 30 seconds. Stop Kafka in the **disposable** project, commit a business transition, and observe pending/age increase. Restore Kafka, confirm publication and one notification/analytics effect per event, then confirm the alert resolves. Inspect `outbox_events` status/attempts/last_error and the publisher logs. Never delete pending or failed rows just to clear the alert.

### Dependency outage

`FleetFlowDependencyUnavailable` fires when the PostgreSQL or Redis probe is `0` for 30 seconds. Stop one dependency only in the disposable project and verify expected readiness/business behavior. Restore it and require new driver location fixes after Redis loss. Keep liveness separate from readiness so a recoverable dependency outage does not restart-loop the app.

`FleetFlowDatabaseReadinessLoss` is the critical alert for the PostgreSQL readiness dependency. The application error and scrape alerts cover sustained API failure and process/management loss. Backup age/failure and certificate expiry remain future signals until their exporters exist.

### Alert rule validation

`ops/monitoring/alerts.test.yml` defines fire-and-recovery cases for application 5xx, database readiness loss, outbox age and consumer quarantine. On 2026-10-14, Prometheus 3.15.0 `promtool check rules ops/monitoring/alerts.yml` found all 9 rules valid and `promtool test rules ops/monitoring/alerts.test.yml` passed all firing/recovery cases. The Windows archive SHA-256 matched the official release asset. This validates rule evaluation only; no live Alertmanager delivery or dashboard scrape was exercised in this prompt because the local Docker Engine endpoint was unavailable.

### Readiness and scrape

`FleetFlowReadinessUnobservable` fires when Prometheus cannot scrape the app for 30 seconds. Check the app healthcheck at the private management port, then inspect app logs, the Compose network, and Prometheus target status. A lost scrape is not by itself proof of a business outage. The Phase 11 drill must check `/actuator/health/readiness` separately and record whether it agrees with the dependency probes.

## Known limits

The Days 1–3 audit strengthens automated owner-delivery proof. The disposable rehearsal compares `alertmanager_notification_requests_total` minus `alertmanager_notification_requests_failed_total` across firing and recovery, and also requires `Notify success` JSON records for `fleetflow-discord`, `discord[0]` and the `FleetFlowOutboxBacklog` group. The aggregate attempted-notification counter alone cannot prove delivery. This follows the pinned [Alertmanager retry implementation](https://github.com/prometheus/alertmanager/blob/v0.34.1/notify/retry_stage.go) and [request metrics](https://github.com/prometheus/alertmanager/blob/v0.34.1/notify/metrics.go). Debug JSON logging is enabled only in that disposable Alertmanager. The retained success artifact allowlists fields and contains no webhook URL. Receiver acceptance is not a human-read receipt.

The dashboard does not directly test a Keycloak login or JWKS rotation; signed OIDC smoke and invalid/expired token tests provide separate identity evidence. Local Prometheus stores seven days of synthetic metrics in its own disposable volume. Grafana's account store is a local demo volume. Neither is a durable business backup. The signed backlog transition was exercised. On 2026-10-09, the operator supplied refreshed 30-minute browser views covering all 12 provisioned panels after signed synthetic traffic; the authenticated datasource check returned samples for all 14 panel queries. Private evidence is `%LOCALAPPDATA%\FleetFlowPhase11\evidence\grafana-browser-populated-top-20261009.png` and `grafana-browser-populated-bottom-20261009.png`. The lower view showed three open synthetic incidents and zero quarantined events; browser rendering does not by itself prove every failure drill. On 2026-10-08, a real stopped-app readiness alert fired and resolved through the optional Alertmanager overlay; its Discord counter recorded two attempts with zero failures after the secret mount was corrected. A deliberately missing backup key produced a nonzero wrapper exit and a successful Discord HTTP response. The operator subsequently supplied a Discord channel screenshot showing the `FIRING` and `RESOLVED` readiness cards and backup `FAILED` notices. A private copy is `%LOCALAPPDATA%\FleetFlowPhase11\evidence\discord-operator-visible-20261008.png`; the receiver-visibility gate is now verified for these messages. A later read of the running Prometheus `/api/v1/alerts` returned an empty alert list, so the screenshot's older firing cards are not evidence of an alert still firing. On 2026-10-09, the actual 02:00 daily backup failed before archive creation; the operator supplied a Discord screenshot of the corresponding failure notice. The private incident screenshot is `%LOCALAPPDATA%\FleetFlowPhase11\evidence\daily-backup-failure-20261009-0200.png`. A repaired manual task rerun succeeded, but the next scheduled trigger remains unobserved.


## Consolidation audit semantics — 2026-10-14

Current execution results supersede the Prompt 2 Docker-blocked snapshot; see [the audit ledger](../phases/production/DAY-1-EVIDENCE-LEDGER.md). Readiness requires PostgreSQL; liveness never depends on PostgreSQL, Redis, Kafka or Keycloak. A process starting while broker DNS is unavailable defers consumer construction on its own scheduler with 1-to-60-second backoff. Publisher retries remain durable and bounded; consumer delivery retries remain three attempts before quarantine. Failed quarantine commit leaves the offset retryable. Consumer startup retries do not count as successful event processing.

`fleetflow_events_quarantined_rows` counts records created in the **last ten minutes**, while the operator inspection route retains the durable metadata history. A clearing alert does not mean an operator disposed of old quarantine. No raw payload is returned or retained for arbitrary poison replay. `fleetflow_events_delivery_total` distinguishes failed delivery attempts from unavailable recovery commits. `fleetflow_events_listener_start_total` counts bounded startup outcomes without broker error text or actor labels.

Backend 429 pressure uses the HTTP meter and route-class counters. Nginx rejects abusive traffic before it reaches Spring; inspect its private JSON access stream separately. It contains only time, generated request ID, method, route class, status and duration. Count `status:429` entries in `docker compose ... logs --since 5m edge` from the operator network, then compare to the load harness's `rate_limit_responses`. Do not enable the base Nginx `main` access log: it includes OIDC query parameters and token hints. Public-edge 429 aggregation/notification belongs to the target monitoring setup; the existing application alert cannot count requests rejected by Nginx.

Consumer lag is not a prerequisite for business commit. The current private runtime exports `kafka_consumer_fetch_manager_records_lag_max` for both fixed consumer clients; the queue panel shows that native lag alongside pending outbox work. To inspect partition offsets, run the pinned broker's `kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group fleetflow-notification-v1` (and analytics group) inside its private container. Backlog age and processed markers remain the release-critical recovery checks. Backup age currently uses `ops/production/check-backup-age.sh`; certificate expiry requires the target TLS probe/timer. Neither is represented by a nonexistent Prometheus series.

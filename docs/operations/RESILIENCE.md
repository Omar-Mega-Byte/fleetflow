# Local demo limits and failure policy

This policy applies to the [Phase 11 local synthetic target](PHASE11_BASELINE.md). It is not a public deployment capacity claim. Role and active-actor checks happen in Spring Security before the MVC route budget. Object checks remain in the business service for requests admitted by that budget. A `429` has one generic body and is keyed only by actor and route class, so it does not reveal whether a resource ID exists.

| Route class | Routes | Caller key | Budget and window | Redis outage |
| --- | --- | --- | --- | --- |
| Ordinary read | Other `GET /api/v1/**` | PostgreSQL actor UUID | 60 requests / 10 seconds | Bounded local per-process budget; durable reads continue. |
| Expensive read | Tracking snapshots, dispatch reads, zone reads | PostgreSQL actor UUID | 30 requests / 10 seconds | Bounded local budget; Redis-dependent handlers return their existing 503. |
| Mutating command | `POST`, `PUT`, `PATCH`, `DELETE` API routes except driver location/heartbeat and local/test-only fixture creation | PostgreSQL actor UUID | 30 requests / 10 seconds | Bounded local budget; durable commands can continue when their own dependencies allow. |
| SSE attempt | `GET .../tracking/stream` | PostgreSQL actor UUID | 6 attempts / minute | Bounded local budget; tracking may still fail when Redis is needed. |
| Location fix | `POST /drivers/me/location` | Exact driver UUID | 30 accepted attempts / minute by the existing atomic Redis Lua policy | `503 REDIS_UNAVAILABLE`; no stale fix is promoted. |
| Heartbeat | `POST /drivers/me/heartbeat` | Exact driver UUID | 60 attempts / minute by the existing atomic Redis Lua policy | `503 REDIS_UNAVAILABLE`; no heartbeat is extended. |

The first four classes use an atomic Redis `INCR`/`PEXPIRE` fixed window shared by app instances pointed at the same Redis, except tracking snapshot GETs. Those always use the bounded in-process budget so a paused Redis cannot consume the snapshot's position freshness window before the handler runs. If Redis fails, each instance uses that same local fixed-window fallback for the other classes. Its map caps at 10,000 actor/class entries and returns `503 RATE_LIMIT_UNAVAILABLE` for new keys beyond that bound. Local budgets are **not shared across instances**, so tracking snapshots and outage traffic have weaker aggregate throttling on a multi-instance deployment. The Phase 11 target runs one app. Route-budget denials use HTTP `429`, `code=RATE_LIMITED`, and an integer `Retry-After` in seconds rounded up from the current Redis or local window. The existing location/heartbeat limit responses retain their specific codes and do not yet report `Retry-After`; clients should wait up to one minute. An exhausted actor budget never uses an order ID, coordinate, token, or exception message as a key or metric label. The route outcome counter labels only class and outcome. These limits are adjustable through `RATE_*_LIMIT` variables; all must be positive.

Resource boundaries in `application.yml`: Tomcat accepts at most 200 connections, queues at most 50 at accept, uses at most 64 request threads, and has a five-second connection timeout. Hikari has 10 connections and a five-second acquisition timeout. Redis commands have a two-second timeout. Outbox Kafka send waits at most five seconds under a lease of at least twice that duration. SSE has 100 total/3 per actor, a five-minute maximum, a bounded 100-item sender queue, a 10-second slow-client limit, and no durable replay. The app's readiness checks PostgreSQL and Redis; liveness checks the application state only. A Redis outage makes readiness fail, even though some durable reads and commands can still succeed through the local route-budget fallback. Kafka remains outside readiness so committed commands can accumulate in the PostgreSQL outbox while the broker is down.

This audit applies only to the six-image trusted-push archive from [run 39131639694](https://github.com/Omar-Mega-Byte/fleetflow/actions/runs/39131639694), source `ff9f4b284c807b6c5f4b88a826ab1513007f50b5`. The Keycloak image has OCI config digest `sha256:433db185614abcdd3813179338494ad9e53f63f45d5b6c4fe31ac6ac4297cbd3` and manifest digest `sha256:92ea04d79b3f06f55a754823216926da8daa4ed3703a3ab1c6e`. The [reconciliation CSV](DAY-4-SUPPLY-CHAIN-RECONCILIATION-2026-10-18.csv) binds each scanner result to this config digest. The original SARIF, SBOM and archive remain in ignored private staging at `target/phase8-review-ff9f4b2/`; all 29 evidence references and six OCI config hashes were checked against trusted CI metadata.

## Reproducible exact-image observations

1. Load the hashed CI archive from the private artifact directory with `docker load --input fleetflow-runtime-images.tar.gz`. Use the archive/config hash procedure in [the promotion handoff](PHASE-8-IMMUTABLE-PROMOTION.md); a base-image index or Docker Desktop's displayed manifest ID is not a substitute for the scanned config digest.
2. Inspect the six OCI layers and run `docker run --rm --network none --entrypoint /bin/bash fleetflow-keycloak-runtime:ci -lc 'find /usr /opt/keycloak -name "libsplashscreen.so" -o -name "libpng.so*" -o -name "libstdc++.so*" -o -name "pcre2test" -o -name "nscd"'`. The result is empty. Searching the exact image's executables and shared libraries for `png_read_end` also returns no match. [OpenJDK 21u's build recipe](https://github.com/openjdk/jdk21u/blob/master/make/modules/java.desktop/lib/Awt2dLibraries.gmk) compiles its bundled libpng into `libsplashscreen` only when `ENABLE_HEADLESS_ONLY` is false; that library is absent from this image. The `java.desktop` legal notice records the source version, not proof that the vulnerable reader was shipped in a runnable native library.
3. Inspect dynamic dependencies with `ldd` across `/usr/bin/*`, `/usr/lib64/*.so*` and the JDK libraries. The only observed dependency on `libsqlite3.so` is `libsoftokn3.so`; the only direct dependencies on `libnss3.so` are the NSS sibling `libsmime3.so` and `libssl3.so`. The exact image has no SQLite JDBC driver in Keycloak jars. Searching image binaries for `sqlite3changeset_apply` and `sqlite3session_create` finds only `libsqlite3.so` itself, not a caller.
4. Run a Java security-provider probe inside the exact image. It reports `SunPKCS11` as **unconfigured and unusable, with zero services**; `Cipher.getInstance("ChaCha20")` selects `SunJCE`; `GraphicsEnvironment.isHeadless()` is true. The Keycloak-owned 26.8.1 class files have no references to `java/awt/Font`, `javax/imageio/ImageIO`, `org/sqlite/` or `com/sun/security/pkcs11`. Their only `ProcessBuilder` references are the Windows service install/uninstall CLI classes. Keycloak's Linux entrypoint and `kc.sh` scripts do not invoke `uniq`.
5. The disposable production-topology browser harness `python scripts/Run-Day1BrowserSmoke.py` passed real HTTPS PKCE login, customer order, authorization, SSE and logout plus Kafka, Redis and database recovery using the same six loaded CI images. Its private result is `target/phase8-keycloak-investigation/day1-browser/browser/result.json`. It reports `PARTIAL` solely because this local rerun did not supply the optional owner-alert webhook; trusted push CI has independently verified owner-alert delivery. During startup and the live browser journey, `/proc/<Keycloak Java PID>/maps` showed no `libfontmanager`, `libsqlite3`, `libsoftokn3`, `libssl3`, `libsplashscreen` or `libpng`. It did show `libnss3`, so NSS is **present and loaded**; the zero-service PKCS#11 configuration, rather than absence of NSS, is the relevant `PK11_Encrypt` evidence.

## Decisions for the seven formerly open rows

| CVE | Exact-image applicability decision |
| --- | --- |
| `CVE-2024-0232` | The vulnerable SQLite JSON parser is present in a native library, but the configured Keycloak service uses PostgreSQL, includes no SQLite Java driver, and did not load SQLite during the signed browser or recovery paths. The only observed native dependency is the inactive NSS soft-token library. No public route supplies SQL to SQLite. |
| `CVE-2024-7531` | NSS itself loads, but the JDK's PKCS#11 provider has zero services and the exact Java ChaCha20 cipher resolves to SunJCE. Neither NSS SSL nor soft-token loaded in the live path. Keycloak is behind the edge and has no QUIC/PKCS#11 configuration; the vulnerable in-place `PK11_Encrypt`/`CKM_CHACHA20` call is not used by this deployment. |
| `CVE-2026-102010` | SARIF maps this to `libgcc`; the flaw is the opt-in C++ PBDS `binary_heap_tag` `erase_if()` template in libstdc++, according to [Red Hat](https://access.redhat.com/security/cve/cve-2026-102010) and [GCC's PBDS documentation](https://gcc.gnu.org/onlinedocs/libstdc%2B%2B/manual/policy_data_structures_using.html). The exact image contains `libgcc_s.so.1` but no compiler, PBDS headers or `libstdc++.so`; the low-level libgcc runtime does not supply the affected template. |
| `CVE-2026-22693` | `libfontmanager.so` and HarfBuzz code exist, so the earlier generic headless-package claim was insufficient. The exact service is headless, Keycloak-owned classes have no font-processing API references, and the font manager did not load during signed browser, order or recovery paths. The required font-shaping call is not part of this configured demo flow. |
| `CVE-2026-46675` | The bundled libpng legal notice says 1.6.58, which [upstream considers affected](https://github.com/pnggroup/libpng/security/advisories/GHSA-qvg3-h654-xq3j), but the vulnerable native reader is compiled into the absent `libsplashscreen` library in OpenJDK 21u. The exact runtime has no `libpng.so` or `png_read_end` symbol. This is a component-absence decision, not a claim that 1.6.58 is patched. |
| `CVE-2026-50812` | The SQLite library exports Session Extension functions, so it cannot be called absent. No other image binary imports `sqlite3changeset_apply`, SQLite did not load during live journeys, and no deployment route accepts a changeset blob. The malformed-changeset apply path required by [Red Hat's advisory](https://access.redhat.com/security/cve/cve-2026-50812) is not used. |
| `CVE-2026-56391` | `/usr/bin/uniq` is present. The defect requires invoking it with `-w`/`--check-chars` and crafted multibyte input. Keycloak's Linux scripts do not invoke it, the only direct `ProcessBuilder` references found in Keycloak-owned classes are Windows service CLI classes, and the public service provides no local shell or command execution. This is a deployment reachability decision, not binary absence. |

These `NOT_AFFECTED` decisions are **narrow**: they cover this exact image, configured PostgreSQL-backed Keycloak service and approved synthetic public routes. Adding FIPS/PKCS#11, NSS soft-token storage, a SQLite driver or changeset consumer, arbitrary provider/theme/font/image processing, shell execution, a different image, or new public routes requires a new scan and review. A short dynamic trace alone does not prove all possible Keycloak features safe; the class, dependency and production-configuration checks above are part of each conclusion. The release owner must independently review the final 28-row CSV before candidate approval.
